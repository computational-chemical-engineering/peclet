# Releasing peclet — the workflow

The repeatable procedure for a *family release* of the suite: every PyPI package (CPU and CUDA),
the HPC containers, the Snellius and LUMI site packages, the GitHub Releases + Zenodo DOIs, the
documentation sites, and the example gallery. It is written so that the next release can be
executed by following it top to bottom. The one-off state for the release currently being prepared
lives in [RELEASE_PREP.md](RELEASE_PREP.md); this file is the durable process.

Releases so far: 0.1.0 / 0.2.0 (2026-07-02), 0.3.0 … 0.6.0 (2026-07-03 … 07-25). The 0.6.0 family
is what PyPI serves today (see §4 for the version table). Everything below was reconstructed from
those releases, the workflows in each repo, and the traps they hit.

---

## 0. What a release consists of

| Artifact | Where | Produced by | Status of the mechanism |
|---|---|---|---|
| **CPU wheels + sdists**: `peclet-core` (sdist only), `peclet-morton`, `peclet-flow`, `peclet-pnm`, `peclet-dem`, `peclet-voro`, `peclet-coupling` (sdist only) | PyPI | each submodule's `.github/workflows/release.yml` on a `v*` tag (cibuildwheel, manylinux_2_28, cp310–cp313, `PECLET_VENDOR_DEPS=ON`; Trusted Publishing) | works (used for every release) |
| **`peclet` metapackage** (== pins on the CPU family; extras `[mpi]`, `[cfd-dem]`) | PyPI | umbrella `.github/workflows/release.yml` on a `v*` tag | works |
| **CUDA wheels** `peclet-flow-cu13` (and, once added, `peclet-dem-cu13`, `peclet-pnm-cu13`, `peclet-voro-cu13`) | PyPI | `cuda-wheel` job in the same `release.yml` (manylinux container + CUDA 13 toolkit, Kokkos-CUDA static, `nvidia-cuda-runtime` dependency wheel, rpath) | works for flow; the other three do not exist yet (§5.3) |
| **Containers** `peclet-cpu`, `peclet-cuda:*-sm80/-sm90`, `peclet-hip:*-gfx90a` | GHCR (`oras://ghcr.io/computational-chemical-engineering/...`) | umbrella `.github/workflows/containers.yml` on a `v*` tag or dispatch | cpu + cuda publish; **hip has failed on every tag** (§8) |
| **Snellius package** | `/projects/0/prjs1022/peclet` (install script + wheelhouse) and the GHCR CUDA image | `tools/hpc/install_snellius.sh` run from the release tag (§7) | script validated for flow; family-wide script is new |
| **LUMI package** | HIP container + `tools/hpc/install_lumi.sh` | §8 | **untested — blocked by the HIP link error** |
| **GitHub Releases** (one per repo + umbrella) → **Zenodo version DOIs** | GitHub / Zenodo | `gh release create` (Zenodo webhook mints the DOI) | works |
| **Docs**: umbrella MkDocs site, per-repo Doxygen, Python API pages | GitHub Pages | `site.yml` (umbrella, on push to main touching docs/), `docs.yml` per repo; `tools/gen_python_api.py` regenerates `docs/python/*.md` | works; the Python pages are regenerated by hand |
| **Example gallery** | `peclet-examples` Pages | authors re-execute and commit `_freeze/`; CI renders only | works; re-execution is manual and slow (§10) |
| **CHANGELOG.md** | umbrella | by hand | stale since 0.2.0 |

Dependency order matters because wheels vendor sibling headers at a pinned tag
(`cmake/PecletDeps.cmake`: `PECLET_TPX_TAG` = core tag, `PECLET_MORTON_TAG`), and the metapackage
pins with `==`:

```
core, morton  →  flow, pnm, dem, voro  →  coupling  →  peclet (metapackage)  →  containers, sites, gallery
```

## 1. Choosing the moment (freeze criteria)

Do not start the workflow until all of the following hold. They are cheap to check and each one has
cost a day when skipped.

1. **No unmerged worktrees.** Every `flow-*`, `tel/*` and other worktree branch is either merged to
   the submodule's `main` or explicitly parked (its work is *not* in the release). List them with
   `git -C <sub> worktree list` and `git -C <sub> branch --no-merged main`.
2. **Every checkout is at `origin/main`.** `tools/release/check_release_state.sh` reports
   `behind`/`ahead` per submodule; all must be 0. (The `flow/` checkout was 55 commits behind
   `origin/main` on 2026-09-04 because the VoF campaign landed through worktrees — a release cut
   from that checkout would have missed the whole campaign.)
3. **Umbrella pointers == submodule HEADs** and the umbrella `git status` is clean apart from the
   known scratch directories.
4. **CI green on `main` of every repo** (`gh run list -R computational-chemical-engineering/<repo> -b main -L 3`).
5. **The local full test matrix (§3) passes** on host *and* CUDA, including the MPI suites.
6. **No open "silently wrong" issues** in `docs/SCALING_ISSUES.md` or `peclet-examples/ISSUES.md`
   that a user would hit through the public Python API in a default configuration. Known
   limitations are fine if they are listed in the release notes.

A convenient moment is right after a campaign has landed and its gallery pages are frozen — the
tests are fresh in memory and the release notes write themselves from the campaign summaries.

## 2. Phase A — freeze and tidy

```bash
cd ~/Codes/suite
tools/release/check_release_state.sh          # versions, tags, pins, PyPI, worktrees, behind/ahead
```

- A1. Merge or park every worktree branch (§1.1). Remove finished worktrees:
  `git -C flow worktree remove ../flow-<name>` (after the branch is merged and pushed).
- A2. Fast-forward every checkout: `git -C <sub> pull --ff-only` for each of
  `core morton flow pnm dem voro coupling`, then `git submodule status` must show no `+`.
- A3. Scratch hygiene. The umbrella working tree carries untracked campaign directories
  (`flow-*`, `sphere-cfd-validation/`, `.sdf-campaign-probes/`, `proposal/`, hash-named dirs).
  They are not committed and do not affect the release, but the sdist of a *submodule* built
  while the repo is a submodule (`.git` is a file) tree-walks and pulls in `build/`/`.venv`. Never
  build a release sdist locally from the submodule checkout — CI builds from a real clone. If you
  must build locally, clone the repo fresh.
- A4. Stale test/scratch files inside submodules (`voro/test_polymesh_sphere.vtu`,
  `voro/python/__pycache__`, dem root-level `verify_*.py` logs): delete or `.gitignore`; never
  `git add -A` (stage named paths only).
- A5. Confirm CI green everywhere (§1.4). Dependabot action-bump PRs need
  `gh auth refresh -s workflow` to merge; merge them *before* the freeze, not during.

## 3. Phase B — fully functioning codes (the test matrix)

Run on the workstation with `OMP_NUM_THREADS=8 OMP_PROC_BIND=false` (the CUDA prefix has an OpenMP
host backend; an unbounded pool on 48 cores is an hour-long trap) and with
`PATH=/usr/local/cuda-13.2/bin:$PATH`. Build trees named `build_rel_*` so they cannot be confused
with campaign trees; **delete them first** — FindPython artefact variables are sticky and a tree
configured against a retired venv fails with "Cannot run the interpreter".

| Project | Suite | Command (host prefix `extern/install/host-openmp`; repeat with `nvidia-cuda`) | Expect |
|---|---|---|---|
| core | serial + MPI halo, migration, load balancing | `cmake -S core -B core/build_rel -DCMAKE_PREFIX_PATH=$P && cmake --build core/build_rel -j && ctest --test-dir core/build_rel --output-on-failure` | all pass, np 1–8 |
| core | Kokkos halo + AMR | `cmake -S core -B core/build_rel_k -DPECLET_CORE_KOKKOS=ON ...` per `core/CLAUDE.md` | all pass |
| morton | doctest + Kokkos + pytest | `ctest --test-dir morton/build_rel`; `python -m pytest morton/bindings/python/tests -q` | all pass; non-BMI2 binary PDEP/PEXT-free |
| flow | kernel unit tests | `cmake -S flow/tests/kokkos -B flow/build_rel_kokkos -DCMAKE_PREFIX_PATH=$P && ... ctest` | all pass |
| flow | distributed (`PECLET_FLOW_MPI`) | `cmake -S flow/tests/kokkos_mpi -B flow/build_rel_kmpi -DMPIEXEC_EXECUTABLE=/usr/bin/mpirun ...` | np 1,2,4 all pass, np=1 bit-exact |
| flow | accuracy/efficiency regression | `PYTHONPATH=flow/build_rel python flow/tests/regression/sdflow_regression.py` | within baseline; do NOT `--update` to make it pass |
| flow | analytic verifications | `flow/scripts/verify_poiseuille_flow.py`, `verify_periodic_spheres_sdflow.py`, `verify_lid_cavity_sdflow.py`, `verify_channel_sdflow.py`, `verify_bfs_sdflow.py` | each prints PASS |
| pnm | extraction + MPI | `pnm/scripts/test_extraction.py ../flow/data/packing_ring.vti`; `tests/kokkos_mpi` np 1,2,4 | 7199 pores; bit-exact |
| dem | kernel + MPI | `dem/tests/kokkos` (8), `dem/tests/kokkos_mpi` (24, host + CUDA); `python dem/verify_packing_spheres.py` | all pass |
| voro | Kokkos + MPI | `cmake -B voro/build_rel -DPECLET_VORO_KOKKOS=ON -DPECLET_VORO_BUILD_PYTHON=ON [-DPECLET_VORO_MPI=ON]`; `OMP_PROC_BIND=false ctest` | all pass (a plain build registers zero tests — not a pass) |
| coupling | Python integration tests | `cmake -S coupling -B coupling/build_rel -DPECLET_COUPLING_TESTS=ON ...; ctest` (needs flow + dem host builds on `PYTHONPATH`) | all pass |
| whole family | import smoke | `PYTHONPATH=<all build dirs> python -c "import peclet.flow, peclet.dem, peclet.voro, peclet.pnm, peclet.core.mpi, peclet.morton, peclet.coupling"` | every `execution_space` reports the intended backend |

Record the counts in `RELEASE_PREP.md` (they become the "tested" line of the release notes).
Anything red is a release blocker unless it is documented as a known limitation.

**Free MPI ctests in CI**: only the OpenMP single-rank builds run on GitHub (no GPU, no MPI
runners). The MPI and CUDA columns of this matrix are a *local* obligation — the release checklist
is the only place they are enforced.

## 4. Phase C — versions

### 4.1 Decide the numbers

Semantic versioning per package; the family version is the metapackage's. Rules used so far:

- **minor** bump when a package gains public Python API or a numerical method (VoF, moving geometry,
  a new drag law), or when it drops one (flow 0.4.0 removed `peclet.flow.pnm`).
- **patch** bump for fixes with no API change.
- A package with **zero commits since its tag keeps its version** (morton and pnm at 0.6.0 time);
  it is not re-released, and its `==` pin in the metapackage stays.
- The metapackage always bumps (its pins changed).

### 4.2 Where versions live (bump every one, in this order)

| File | Field | Notes |
|---|---|---|
| `<sub>/pyproject.toml` | `version` | the PyPI version; **tag must equal `v<version>`** |
| `<sub>/packaging/*_init.py` (`__version__`) and `morton/bindings/python/peclet/morton/__init__.py` | `__version__` | must match pyproject (0.2.0 shipped with a stale core `__version__`) |
| `flow/packaging/pyproject-cuda.toml` (and each future `*-cu13`) | `version` | same number as the CPU package |
| `<sub>/Doxyfile` | `PROJECT_NUMBER` | Doxygen sites show it |
| `<sub>/CITATION.cff`, umbrella `CITATION.cff` | `version`, `date-released` | Zenodo reads these |
| `<consumer>/cmake/PecletDeps.cmake` | `PECLET_TPX_TAG`, `PECLET_MORTON_TAG` | flow, pnm, dem, voro, coupling: pin to the **new core/morton tags** — voro shipped 0.4.0 pinned to a stale core tag |
| umbrella `pyproject.toml` | `version`, every `==` pin, extras | publish the members first — the pins must resolve on PyPI |
| `docs/containers.md`, `containers/README.md`, `containers/submit/*.slurm` | image tags in the `apptainer pull` lines | today they still say `0.1.0` |
| `CHANGELOG.md` | new section | Keep-a-Changelog format; one section per family version |

`tools/release/check_release_state.sh` prints all of these next to each other so a mismatch is
visible before tagging.

## 5. Phase D — documentation and the Python API

### 5.1 Docstrings and generated API pages

1. Build the whole family (host prefix is enough) and run
   `tools/release/audit_docstrings.py` — it imports every `peclet.*` module and lists bound
   callables without a docstring, plus docstrings that still say `sdflow`/`vorflow`/`tpx`/
   `peclet.flow.pnm`. Fix in the binding TUs (`<sub>/src/*_bindings.cpp`, `core/python/*_bindings.cpp`).
2. Regenerate the Python API pages: `python tools/gen_python_api.py docs/python` with the family on
   `PYTHONPATH`. Check that `PAGES` in that script still lists every module (it lacked `peclet.pnm`
   at one point, and lacks `peclet.coupling` and `peclet.core.geom` today) and that `mkdocs.yml`
   nav has a page for each.
3. `mkdocs build --strict` must pass (the Site workflow runs exactly that).

### 5.2 Prose

Update, in this order, and read each one end to end (they drift in small factual ways):

- umbrella `README.md`, `docs/index.md`, `docs/DEPLOYMENT.md`, `docs/containers.md`,
  `docs/PORTABILITY.md`, `docs/SNELLIUS.md`, `docs/LUMI.md`, `containers/README.md`;
- each submodule `README.md` (badges, install line, feature list) and `CLAUDE.md` build/test sections;
- `CHANGELOG.md` — write the family section from the per-package `git log <old-tag>..HEAD --oneline`
  and the campaign summaries in `docs/*_PLAN.md`;
- `CLAUDE.md` links (a dead link to `docs/CUDA_RETIREMENT.md` has been there since 0.1.0).

The audit list for the current release is in `RELEASE_PREP.md`.

### 5.3 CUDA wheel coverage (decision point)

Only `peclet-flow-cu13` exists. A symmetric CUDA family needs a `cuda-wheel` job + a
`packaging/pyproject-cuda.toml` in **pnm, dem, voro** (copy flow's job; dem additionally builds
ArborX into the prefix; each module's rpath is `$ORIGIN/../../nvidia/cu13/lib`, one level per
package depth — pnm was wrong once) and a `peclet-cu13` metapackage (umbrella
`packaging/pyproject-cu13.toml` published by a second job of the umbrella release workflow).
Per-package prerequisites: the module must survive interpreter teardown after a solve (dem's
atexit-finalize pattern; flow had a teardown abort), and the PyPI Trusted Publisher must be
registered for the new project name *before* tagging (a new name publishes fine with no extra
registration — pnm 0.1.0 proved it — but only if the workflow's `environment: pypi` is configured).

Validate locally before CI: `PATH=/usr/local/cuda-13.2/bin:$PATH CMAKE_PREFIX_PATH=$PWD/extern/install/nvidia-cuda pip wheel ./dem`
into a fresh venv, then run a verify script on the GPU.

## 6. Phase E — publish to PyPI

Per repo, in dependency order (§0). For each:

```bash
cd <sub>
# 1. version bumps (§4.2) committed on main, pushed
git push origin main
# 2. tag == pyproject version
git tag v<X.Y.Z> && git push origin v<X.Y.Z>
# 3. watch the Release workflow (sdist + wheels [+ cuda-wheel] + publish)
gh run watch -R computational-chemical-engineering/peclet-<sub> $(gh run list -R computational-chemical-engineering/peclet-<sub> -w Release -L 1 --json databaseId -q '.[0].databaseId')
# 4. confirm on PyPI (the JSON endpoint caches for minutes — use pip)
pip index versions peclet-<sub>
```

Then the umbrella: bump `pyproject.toml` pins + version, bump the submodule pointers
(`git add core flow ...` by name), commit, push, tag `v<family>`, watch `Release` **and**
`Containers`, then §9.

Traps recorded from 0.1.0–0.6.0:

- cibuildwheel 4.x dropped cp38: keep `requires-python >= 3.10` and the build selector in sync.
- macOS Intel runners queue for 40+ minutes and gate publish — morton dropped `macos-13`; do not add it back.
- `skip-existing: true` in the flow publish step lets a partial upload be completed (e.g. adding the cu13 wheels after the CPU files); leave it.
- A `pypi/pyversions` badge renders "missing" without trove classifiers; the static python badge is deliberate.
- **Smoke test in a fresh venv** after the metapackage is live:
  `python -m venv /tmp/rel && /tmp/rel/bin/pip install peclet==<family> && /tmp/rel/bin/python -c "import peclet.flow, peclet.dem, peclet.voro, peclet.pnm, peclet.morton"`, then run one gallery example
  (`poiseuille-ibm`) against it; repeat with `peclet-flow-cu13` on the GPU box.

## 7. Phase F — Snellius package

What "a release for Snellius" means, in decreasing order of user convenience:

1. **The GHCR CUDA images** `peclet-cuda:<family>-sm80` (A100) and `-sm90` (H100), pulled with
   `apptainer pull oras://...` and launched by `containers/snellius-run.sh` / `containers/submit/snellius.slurm`.
   Multi-node runs need the host OpenMPI/UCX bind (the image bundles OpenMPI 4.1.6; match the site module).
2. **A site-built install** in the project space, from the release tag, with the validated 2024a
   toolchain (`docs/SNELLIUS.md`): `tools/hpc/install_snellius.sh <tag> h100|a100|cpu`. It clones
   the umbrella at the tag, bootstraps Kokkos for the backend, and pip-installs the whole family
   (`PECLET_*_MPI=ON`) into `$SUITE/.venv`, leaving a **wheelhouse** at
   `/projects/0/prjs1022/peclet/wheelhouse/<tag>-<backend>/` so project members can
   `pip install --no-index --find-links <wheelhouse> peclet-flow` into their own venv without
   rebuilding. Wheels built on Snellius are **site-specific** (linked against the module OpenMPI,
   CUDA 12.6, sm_80/sm_90) and must never be uploaded to PyPI.
3. **Source build** by the user following `docs/SNELLIUS.md` (the fallback; unchanged).

Release steps (billed: one build job per backend ≈ 1 GPU × ≤2 h; queue the CPU build on `genoa`):

```bash
ssh snellius
cd /projects/0/prjs1022/peclet && git clone --branch v<family> --recurse-submodules https://github.com/computational-chemical-engineering/peclet.git suite-v<family>
sbatch --nodes=1 --gpus-per-node=1 --ntasks-per-node=1 suite-v<family>/tools/hpc/install_snellius.sh v<family> h100
sbatch -p gpu_a100 suite-v<family>/tools/hpc/install_snellius.sh v<family> a100
sbatch -p genoa   suite-v<family>/tools/hpc/install_snellius.sh v<family> cpu
```

Then the **smoke job** `tools/hpc/smoke_snellius.slurm` (4 ranks on one node: `has_mpi: True`,
`execution_space: Cuda`, flow `init_mpi` bit-exact k vs np=1, dem `step_mpi`) and record the job
ids + numbers in `docs/SNELLIUS.md` "Validated releases". Give the release its **own remote tree**
(`suite-v<family>`), never the shared campaign checkout — concurrent sessions have rebuilt the
shared `build_cuda_mpi` on top of each other's uncommitted sources.

Snellius rules that apply here: positional sbatch arguments (leading `VAR=x sbatch` is silently
dropped), `--gpus-per-node=1` for a 1-GPU job (billing is per allocated GPU), `-DPython_EXECUTABLE`
with a capital P, `-DMPIEXEC_EXECUTABLE=$(which mpirun)`, `FRESH=1` when the CUDA module changed.

## 8. Phase G — LUMI package (untested)

State: **no peclet-hip image has ever been published.** The `hip-gfx90a` container job fails at
link time in every release run since 0.3.0 with

```
ld.lld: error: undefined hidden symbol: vtable for Kokkos::Impl::SharedAllocationRecord<Kokkos::HIPSpace, ...>
ld.lld: error: undefined hidden symbol: vtable for std::_Sp_counted_ptr_inplace<peclet::core::halo::GridHaloTopology<3>, ...>
```

`-Wl,--no-gc-sections` (present in flow/pnm/voro/coupling CMake since 0.2.0) did **not** fix it, so
the diagnosis "gc-sections drops the vtables" is refuted. The references are emitted with hidden
visibility because nanobind sets `CXX_VISIBILITY_PRESET hidden` on the module target
(`nanobind_set_visibility`), and under hipcc/lld the vtables of these header-instantiated classes
are not emitted in the same object. The same link will fail for a source build on LUMI, so **this
blocks every LUMI delivery, container or not.**

Experiments, in order of plausibility (each is one `workflow_dispatch` of `Containers` with
`only=hip`, `push=false`, ≈25 min; no GPU is needed to link):

1. After `nanobind_add_module(...)` in flow/pnm/dem/voro/coupling `CMakeLists.txt`, gated on
   `Kokkos_ENABLE_HIP`: `set_target_properties(<target> PROPERTIES CXX_VISIBILITY_PRESET default)`.
2. Bootstrap Kokkos for `lumi-hip` as a shared library (`-DBUILD_SHARED_LIBS=ON` in
   `tools/bootstrap_deps.sh`), so the Kokkos vtables come from `libkokkoscore.so`.
3. Relocatable device code: `-DKokkos_ENABLE_HIP_RELOCATABLE_DEVICE_CODE=ON` + `-fgpu-rdc` on the modules.
4. Drop `-fvisibility-inlines-hidden` if the ROCm clang adds it; check `hipcc --verbose`.

Until one passes, the LUMI deliverable of a release is:

- `docs/LUMI.md` — the site recipe (Cray PE modules, `hipcc`, `craype-accel-amd-gfx90a`, ROCm ≤ host driver, Cray-MPICH ABI bind model) with a banner **"untested — no LUMI allocation yet"**;
- `tools/hpc/install_lumi.sh` — the source-install script mirroring the Snellius one (untested);
- `containers/hip.def` + `lumi-run.sh` + `submit/lumi.slurm` as they are, with the known-failure note in `docs/containers.md`.

The release notes must say this in one sentence. When LUMI time is granted: run experiment 1 on a
LUMI login node first (link only, seconds), then the smoke job, then re-dispatch the container job.

## 9. Phase H — containers, GitHub Releases, Zenodo, sites

1. **Containers**: the umbrella tag triggers `containers.yml` (cpu, cuda-sm80, cuda-sm90 ≈ 20 min
   each; hip fails — expected until §8 is fixed, and it does not block the others because the matrix
   is `fail-fast: false`). Verify: `apptainer pull oras://ghcr.io/computational-chemical-engineering/peclet-cuda:<family>-sm90`
   on Snellius and run the smoke job through `containers/snellius-run.sh`. The images install
   **flow, dem, voro, core, morton only** — add `pnm` and `coupling` to `cpu.def`/`cuda.def`/`hip.def`
   (§ RELEASE_PREP) so the container family matches PyPI.
2. **GitHub Releases**: one per repo at its new tag + the umbrella, body = the CHANGELOG section
   (`gh release create v<X> -R computational-chemical-engineering/peclet-<sub> --title "peclet-<sub> <X>" --notes-file <notes>`).
   Zenodo mints a version DOI per repo within minutes; the concept DOIs in the badges and
   `CITATION.cff` do not change. Add the new version DOIs to `CITATION.cff` `identifiers:` if you keep that list.
3. **Sites**: the umbrella `Site` workflow runs on the docs push; each repo's `docs.yml` on its
   push. Check `https://computational-chemical-engineering.github.io/peclet/` shows the new
   version in the install page and that the Python API pages carry the new methods.
4. **Memory/notes**: update `docs/SNELLIUS.md` "Validated releases", `RELEASE_PREP.md` → archive as
   `docs/releases/<family>.md`, and reset `RELEASE_PREP.md` for the next cycle.

## 10. Phase I — the example gallery (after the release, not blocking it)

The gallery pins nothing: every bootstrap cell does `pip install peclet` (latest) unless
`PECLET_LOCAL_BUILD` points at a build tree, and the site renders from committed `_freeze/`
outputs. So a release cannot break the published site, but it *can* make a page's Colab button
run a different solver than the frozen numbers came from. The obligations are therefore:

1. Before tagging, produce the **re-check list** with `tools/release/audit_examples.py`
   (or the table in `RELEASE_PREP.md`): for each page, the peclet symbols it calls and whether
   each exists in the tagged bindings. Pages calling symbols that only exist on `main` were rendered
   against a local build and become runnable on PyPI *only* with this release — they are the ones
   to re-execute first, because their frozen output was produced by a pre-release build.
2. After the metapackage is live: re-execute the list in priority order in a fresh venv
   (`pip install peclet==<family>`; for GPU pages `peclet-flow-cu13`), page by page with
   `render_example.sh <slug>` (clears the page's freeze) — note that editing even a subtitle
   invalidates a freeze, and `quarto` exits 0 on a figure-cell error, so grep `_site` for
   `cell-output-error` before committing. Commit each page's `_freeze/` (force-add npz/mp4 assets).
3. Pages that need a build the wheels do not provide (MPI, Snellius, `peclet.coupling`,
   `core.geom`) stay frozen and say so in their bootstrap comment; they are re-checked when the
   corresponding site package (§7) is installed.
4. Close or update the `ISSUES.md` entries the release fixes; open new ones for what the re-run finds.

## 12. Execution advice

- **Run it as a two-day block**, not interleaved with development: day 1 = Phases A–D (tests,
  docs, versions) on the workstation; day 2 = Phases E–H (publish, containers, Snellius). Snellius
  builds queue for up to an hour — submit them first thing on day 2 and do the PyPI publishing while
  they run; they only need the tag to exist.
- **One driver, one checklist.** Copy the phase headers of this file into `RELEASE_PREP.md` as a
  checkbox list and tick them in the order given; parallel agents may prepare docs and tests, but
  the tag/publish steps are sequential by dependency and should be done by one session.
- **Tags are permanent.** If a release workflow fails after the tag exists, fix and re-run the
  workflow (`gh run rerun --failed`); never delete and re-push a tag that reached PyPI. A broken
  published package gets a patch release.
- **Do not touch numerics during the release window.** Version bumps, docs and packaging only; a
  numerical fix found in Phase B is either a blocker (fix, re-run the matrix from the top) or a
  known limitation (release notes).
- Expected wall time from tagging the first member to a live metapackage: about 90 minutes (the
  CPU wheel builds compile Kokkos per Python version; the CUDA job is the long pole at ~40 min).
